# 2026.243.1128 — docs: stop pinning a CalVer in skill usage examples

## Summary

A usage example inside this repo's skill document (`content:` block) pinned a hardcoded
CalVer. That version is guaranteed to rot: it cannot be kept current without minting a
release for every documentation edit, and while stale it teaches a version nobody should
copy. It now reads `:vTAG`, which never goes stale and fails fast if pasted literally
rather than silently building against an old pin.

That matters here specifically because these blocks are **skill documents read by agents**,
where a stale-but-valid version is the more dangerous of the two failure modes.

The ref changed in THIS diff:

```

            becomes  @github.com/opencharly/pod-postgresql:vTAG
```

The candy's own CalVer advances from `2026.243.0100` to `2026.243.0909` because the skill content changed,
and changed content must ship under a new version rather than reuse a released one.

## Proof these refs are prose, not dependency edges

This is the load-bearing claim, so it is shown rather than asserted. Each changed ref sits
inside a block scalar opened by a `key: |` line, which YAML treats as opaque text:

~~~~
  ref at line 195:  - '@github.com/opencharly/pod-postgresql:vTAG'
    enclosed by  line 134: content: |   <- block scalar; YAML treats all of it as TEXT
    and by       line 191: (a yaml code fence)  <- a fenced example INSIDE that text
    decisive: lines between 134 and 195 with indent < 12 (which would CLOSE the block): 0
    => the block never closes before the ref; it is text, never resolved

    $ awk 'NR>134 && NR<195 && $0!~/^ *$/ {match($0,/^ */); if (RLENGTH<12) print NR}' charly.yml | wc -l
    0
    ^ zero lines are indented < 12 (the block's CONTENT indent)
      so the block scalar opened at line 134 is still open at line 195.

    --- sed -n '134,137p;193,195p' charly.yml ---
      134 |         content: |
      135 |             # vectorchord -- VectorChord vector similarity extension for PostgreSQL
      136 |             
      137 |             ## Candy Properties
      ... |
      193 |             my-image:
      194 |               candy:
      195 |                 - '@github.com/opencharly/pod-postgresql:vTAG'
~~~~

charly parses `content:`/`description:` as strings; it never resolves a ref inside one. The
mechanical confirmation is the resolving-ref count below, which is byte-identical across the
change.

**On `git diff`'s hunk header.** The `@@ ... @@` suffix on these hunks names a key that looks
structural (e.g. `deploy-skill:`), and it is tempting to read that as proof the ref is a real
dependency entry. It is not: that suffix is git's *context heuristic* — the nearest preceding
line that is less indented and matches its pattern. Inside a block scalar every line is opaque
text, so the heuristic latches onto whatever the prose happens to contain. The two checks above
read the file's actual structure; the hunk header does not.

Anyone can verify independently — the enclosing `key: |` opener and the fence line are quoted
above with their line numbers, so `sed -n '<opener>,<ref>p' charly.yml` shows the whole block.

## Empirical proof — charly's own behaviour, with a negative control

Structural argument aside, the authoritative test is what charly does. `:vTAG` is not a
resolvable tag, so if these refs were dependency edges, validation would FAIL on them.

| # | tree | result |
|---|---|---|
| A | this repo, unmodified | `charly box validate` exit **0** |
| B | this repo, the changed refs at `:vTAG` (i.e. THIS PR) | exit **0** |
| C1 | control: `pod-hermes`, unmodified (5 real resolving refs) | exit **0** |
| C2 | control: `pod-hermes`, a REAL ref set to `:vTAG` | exit **1** |

C2's failure is the control that gives B its meaning — it proves charly does resolve and does
reject an unresolvable tag:

```
$ sed -i "s|layer-ffmpeg:v2026.239.1614|layer-ffmpeg:vTAG|g" charly.yml
$ charly box validate ; echo "exit=0"
charly: error: command "validate": validation error: downloading
  github.com/opencharly/layer-ffmpeg:vTAG: InvokeProvider refs:refs op=resolve: resolving ...
exit=1
```

So charly fails hard on an unresolvable REAL ref (C2) and does not notice these ones (B).
That is only possible if it never resolves them — which is the claim, demonstrated rather
than argued.

## How tested

**The set of refs this file RESOLVES is unchanged** — 1 before, 1 after. Only prose
moved. This is the property that matters, because a doc example and a real pin are
indistinguishable by shape (both render as `  - '@github.com/opencharly/x:vY'`), so the
rewrite is block-scalar aware and re-parses the file after writing, refusing to save if the
resolving set differs.

`charly box validate` on the **final committed tree**, with the `v2026.238.1242` binary this repo pins:

```
$ charly box validate
$ echo $?
0
```

Exit code read from charly directly, never through a pipe — a piped `| tail` reports the
pipe's status rather than the command's.
